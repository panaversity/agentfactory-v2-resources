# 20.10 Should the AI design the screen?

*Going further. Named, and A2UI taught in outline. Neither is built.*

**In everyday life.** A restaurant can print a fixed menu, let the chef pick from a list of approved dishes each day, or let the chef cook anything. Each gives more freedom and less control.

**What you will learn.** Three ways an AI can shape a screen, the one most teams choose, and A2UI, an open standard for that choice, with the ways it works with MCP.

**Why it matters.** Someone will ask for "a screen the AI builds itself". You should know what that costs, and that you do not have to invent the safe way.

### What are the three ways?

| Way | How it works | Freedom | Control |
| --- | --- | --- | --- |
| Fixed | You build the screen. The AI fills in the data, as in this chapter | Low | Highest |
| From approved parts | You list the parts the AI may use, such as a table, a card and a button. The AI writes a short description of which parts to show, and the page draws only those | Medium | High |
| Open | The AI writes the page itself, and the AI app shows it in the sandbox | Highest | Lowest |

The middle way is usually the right one. Brightline could approve five parts: an invoice card, a vendor card, a due-date list, a total, and a button that calls a tool. When Hannah Price, Cedar Ridge's controller, asks for "the overdue ones, by vendor", the AI builds that screen from those five parts only.

*Figure 20.11. Three ways an AI can shape a screen, from most control to most freedom.*

### How does the middle way work?

In four parts:

1. **A catalog.** You list the parts the AI may use, and what each part can do.
2. **A description.** The AI writes a short description that uses only parts from the catalog, and sends it as a tool's input.
3. **Streaming, if the AI app sends it.** Some AI apps send the description while the AI is still writing it, so the screen fills in live. The page must also work without it.
4. **A registry.** The page maps each part's name to real code, and draws it.

### What is A2UI?

A2UI is an open standard for exactly this middle way, so you do not have to invent one. It is Google's open protocol for generative screens: the agent describes what to show, and each app draws it with its own native components. In outline:

- **Data, not code.** The agent sends messages that create a screen, update its components and update its data.
- **Approved parts only.** An app draws only components from a catalog it accepts, so the agent can place and configure only the parts a developer registered.
- **Data bound to parts.** A data update refreshes the parts bound to it, without drawing the screen again.

**One request, start to finish.** Hannah asks for "a summary of our overdue invoices, by vendor".

1. **The agent does not write a page.** It sends A2UI messages: create a screen, add a card, a table and a button from the basic catalog, and fill the table from the data.
2. **The app draws those parts with its own components,** in its own style. Nothing the agent sent is code.
3. **New numbers arrive as a data update.** The table refreshes, and the rest of the screen stays.
4. **Hannah presses the button.** The app turns the press into an action the agent receives, and the agent decides what comes next.

Google released A2UI 1.0 on November 11, 2026, calling it the first stable version. It adds two-way function calls, so a screen can check something, such as whether a time slot is free, while the person works. It also adds accessibility support and extensions for more metadata. Code libraries that draw A2UI screens, called renderers, exist for the web (React, Angular, Lit), Flutter, SwiftUI and, coming for 1.0, Jetpack Compose. As of November 26, 2026, the A2UI project lists 1.0 as its current version and 0.9.1 as the previous one.

### How does A2UI work with MCP?

The A2UI project now documents four ways. Three of them matter to a connector builder:

- **A2UI over MCP.** A tool returns A2UI as data, marked `application/a2ui+json`, and an AI app that draws A2UI itself shows it.
- **A2UI in MCP Apps.** An MCP App carries its own A2UI renderer and draws the A2UI it fetches through tool calls. This works in any AI app that shows MCP Apps.
- **MCP Apps in A2UI screens.** An A2UI screen holds an MCP App in a sandboxed frame.

The fourth is an A2UI app of your own whose buttons call a connector's plain tools.

Few AI apps draw A2UI themselves today, so the second way is the practical one. Google reports that Alation already shows A2UI screens in Claude this way, and that Gemini Enterprise's agents already use A2UI.

### Does a screen from approved parts change whose call a button makes?

No. The same rule holds for all three ways: every call the screen makes is checked like any other. A press on an A2UI part becomes an action, and any tool call that follows goes through the AI app with the person's token, as in 20.4. Approved parts limit what the screen can look like. The connector still decides what each person may do.

**The operating rule:** if the AI must shape the screen, let it choose from parts you approved, such as A2UI drawn inside an MCP App, never let it write the page, and keep every rule about who may do what in the connector.
