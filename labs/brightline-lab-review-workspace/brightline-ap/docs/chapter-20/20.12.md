# 20.12 Who approves a skill from a server?

**In everyday life.** You sign a contract on Monday. On Wednesday someone swaps page 3. Your signature does not cover the new page, and you sign again only after you read it.

**What you will learn.** Who approves a skill that a server sends, what the approval covers, and the rules a connector must keep. You test it in Lab 20, Task 11.

**Why it matters.** This chapter asks who each call acts as. A skill raises the same question about instructions: the model follows steps that Brightline wrote, inside Cedar Ridge's AI app. Someone at Cedar Ridge must decide to let them in, and that decision must not cover a later change without a new look.

**One request, start to finish.** On Monday, Luis approves `invoice-triage`. On Thursday, Ana adds one line to its rules file, and Brightline deploys.

1. **Luis's AI app lists the skills again.** The manifest has a new fingerprint for `references/rules.md`.
2. **The approval no longer counts,** because it covered the old set of files and fingerprints.
3. **The AI app asks Luis again,** and shows what changed.
4. **He approves again.** Thursday's run follows the new rule.

### Who approves, and what does the approval cover?

The extension says what an AI app must do. Whether a given AI app does it today is a separate question. 20.16 says where the extension is turned on, and Lab 20's Task 11 has you watch what your own AI app does. The connector's job is the same either way: publish a correct manifest. Under the extension, the AI app treats skill content as untrusted input. Running code or granting tool permissions from a skill needs the explicit approval of the person using the AI app, for that skill. For a skill that holds only instructions, such as `invoice-triage`, each AI app decides whether to ask. Luis's does. A saved approval covers the exact set of file addresses and fingerprints. A changed, added or removed file cancels it, and the AI app must ask again before loading the skill.

The AI app also tags each loaded skill with the connector it came from, and must not let two skills with the same name silently replace each other.

### What must the connector do?

- **Publish a complete manifest,** computed from the bytes it serves. A skill built at the moment it is asked for can be marked `"dynamic"`, but AI apps may decline it.
- **Keep each skill small:** at most 512 files and 16 MiB. AI apps must support at least that much.
- **Use names that will not collide,** such as `brightline-invoice-triage`, not `triage`.
- **Batch skill changes.** Every change makes every customer approve again. Version the skill, as in 16.6, and say what changed.

### How far along is it?

The extension's stage is Beta (20.1). The written proposal behind it, which the MCP project numbers SEP-2640, is closed as final, so its details may still change but its design is agreed. Support in AI apps and code libraries is still being built. 20.16 says where it works today. Until support spreads, a connector can also offer each skill as an ordinary tool that returns its instructions, and remove that copy once AI apps load skills natively. A skill offered as a tool has no manifest check, so say so in the tool's description.

**At work.** In Lab 20, Task 11, Ana changes one rule. OpenCode's test lists the skills before and after and checks that the fingerprint in the manifest changed.

**The operating rule:** ship skills with complete manifests and names that will not collide, change them in batches, and expect every change to be approved again.

**Do this now.** Think of the last three changes you made to a skill. Write how many times each customer would have approved again, and how many times if you had shipped them as one version.
