# F10. How today's tools realize it, in detail

The product-by-product detail behind 18.17, checked on each maker's own pages on November 2, 2026, against MCP revision 2026-07-28.

**What kind of evidence this is.** Each statement below is the product's own documented behavior, read on its first-party page on November 2, 2026, and numbered to its source. "Not documented" means the authors read the page and did not find it, not that the product lacks it. Your Lab 18 port notes, in `ports/ch18.md`, are the test of each.

### How each one differs from the specification

> *Anthropic.*
>
> - *Claude Code.* Signs in from `/mcp` or `claude mcp login <name>`, after a 401 or 403 marks a server as needing it. Follows protected resource metadata, then the sign-in server's metadata. Supports Client ID Metadata Documents and finds them by itself, and pre-registered clients with `--client-id`, `--client-secret` and `--callback-port`, which sets a fixed `http://localhost:PORT/callback`. Asks for a refresh token when the sign-in server offers one. *Adds* an automatic refresh and one retry on a 401.
> - *Relaxes nothing we found, but* an older setting that adds a fixed header to every request (`headersHelper`) wins over sign-in when it sets `Authorization`. A leftover one from Chapter 17's shared key would silently replace your token. Remove it.
> - *The Messages API's MCP connector* takes an `authorization_token` per server. It does not run a sign-in. Your program gets the token, refreshes it, and passes it in. It is in beta on every model (field guide F5 has the exact setting), and Anthropic's option to keep no copy of your data does not cover it. Chapter 20 keeps such tokens per user and company.
> - *Status and price.* Claude Code needs a Claude plan or API billing. The connector is billed like any Messages request.

> *OpenAI.*
>
> - *Codex.* `codex mcp login <name>`, with `--scopes` for one sign-in. Uses a Client ID Metadata Document when the sign-in server's document says three things. It supports these documents, it accepts apps that have no secret of their own, and it accepts Codex's return address on any port. Its document lives at `https://chatgpt.com/oauth/codex/<callback_id>/client.json`. `--oauth-client-registration cimd` forces that route for one sign-in. Checks the issuer before exchanging the code. A pre-registered client uses `--oauth-client-id`, and a client secret given with `--oauth-client-secret` is **saved in `config.toml`**, so keep pre-registered Codex clients public, with no secret.
> - *The Responses API's MCP tool* takes the token in an `authorization` field. OpenAI does not store it, so your program sends it with every request. Like Anthropic's, it does not run a sign-in.
> - *Status and price.* Which ChatGPT plans include Codex was not rechecked on November 2.

> *Open source.*
>
> - *OpenCode version 2.* Sign-in is on by default for remote servers. `opencode mcp auth <name>`, or `/mcps`, signs in through the browser with PKCE, and `opencode mcp logout <name>` signs out. Uses a configured `client_id` first, then a Client ID Metadata Document when the server supports it and no `redirect_uri` is set. Setting `redirect_uri` turns Client ID Metadata Documents off.
> - *Falls back to the older registration route* this book does not teach. Brightline's sign-in server does not offer it, so if OpenCode's metadata document is not accepted, pre-register a client for it (field guide F7).
> - *Security.* The issuer check is not documented. Record what your run shows in `ports/ch18.md`.
> - *Status and price.* Free and open source. You pay for the model.

### Where the sign-in runs

> **Better Auth, on a Cloudflare Worker, with D1.** Better Auth is an open-source sign-in **library** for TypeScript: code you run inside your own program, not a service you sign up for. You add features as plugins, which here means Better Auth's own add-ons, not Chapter 16's plugins. Brightline's sign-in server is a Cloudflare Worker (17.11) running Better Auth 1.7.15, the newest stable release on November 2, 2026. Version 1.8 is in beta and not used.
>
> - *Four plugins.* `mcp()` makes it an OAuth authorization server for an MCP connector, and its own page says not to add the general OAuth provider plugin beside it. `jwt()` seals tokens and publishes the public keys, with the private halves encrypted. `organization()` adds companies, memberships and roles. `cimd()` accepts Client ID Metadata Documents, with the MCP 2026-07-28 profile.
> - *Implements, per the specification.* Protected resource metadata and authorization server metadata, PKCE, the `resource` parameter with the token's audience set to it, scopes, short-lived tokens and refresh tokens replaced on every use, issued only when the app asks for `offline_access`. The older registration route is off unless you turn it on, and the lab never does.
> - *What it leaves to you on Workers.* Its secure fetcher for Client ID Metadata Documents is for Node only. Other runtimes, Workers included, "must provide the equivalent secure transport", which a Worker cannot fully do because it cannot choose the exact network address it connects to. The lab therefore accepts documents only from a short list of known hosts (18.5, field guide F3).
> - *What it cannot do with signed tokens.* Its own page says signed access tokens "cannot be revoked server-side", which is why 18.6 keeps them to 10 minutes.
> - *D1* is Cloudflare's database service. Each D1 database is a SQLite database, a small kind of relational database (18.8) that many phones and apps use, run by Cloudflare for you. A Worker reaches it through a binding, Chapter 17's word for a named link from a Worker to a platform resource. Better Auth uses that binding directly. Free plan: 10 databases, 500 MB each, 5 GB in all, 5 million rows read and 100,000 rows written a day, and 50 queries per Worker request. Brightline's sign-in server uses a tiny fraction.
> - *Free plan limits that matter here.* Workers give 10 ms of processor time per request on the free plan, with some flexibility for a Worker that "infrequently runs over". Password hashing at sign-in is the heaviest step. The authors measured about 80 ms of processor time per sign-in in Cloudflare's local runtime, roughly 8 times the 10 ms. **Not yet run online:** whether a deployed sign-in still succeeds, or fails with Error 1102. It needs a person to deploy and sign in. The connector fetches the sign-in server's public keys through a **service binding**, a direct link between two Workers in one account that does not go through a public address. Cloudflare's own Rate Limiting binding, for rule 5 in 18.12, is not listed in the free plan's features. Lab 18 tries it, and if it is refused, uses an in-memory limiter online and records that the limit is then counted per copy, not across all copies.
> - *Alternatives.* Cloudflare's own Workers OAuth Provider library runs an authorization server inside a Worker. It supports Client ID Metadata Documents (with a setting that limits its fetches to public addresses), and replaces refresh tokens on every use. A hosted identity service runs the sign-in server for you, for a monthly price. All three serve the same connector unchanged, because the connector checks standard tokens against standard public keys.
> - *Status and price.* Better Auth is free and open source. Workers and D1 have the free plans above.

### The tenancy models, product by product

All three tenancy models from 18.9 work with every AI app above, because each model is only a question of what address the connector has and what audience its tokens carry. The difference is in the sign-in server: Better Auth's `organization()` plugin, with consent stored per company, supports the first model directly. The second model needs one connector address per company in the sign-in server's settings, so check that the pinned version accepts several before choosing it. The third model is one more deployment of everything.

### Watch this: DPoP

> **DPoP** (Demonstrating Proof of Possession, RFC 9449) binds a token to a key held by the AI app, so a stolen token is useless without that key. The app signs a small proof for each request. The MCP specification does not require it in revision 2026-07-28. Better Auth's connector helpers enforce it when a token is bound this way. Watch for AI apps adopting it, and for a later MCP revision asking for it. Brightline does not use it yet.
