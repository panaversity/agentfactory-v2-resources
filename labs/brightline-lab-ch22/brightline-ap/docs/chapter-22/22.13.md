# 23.13 What keeps a leaked key from working forever?

**Part D. Safe to sell: keys, refresh, schedules and loops.** *Half 2, Milestone 2. Read this half before you sell a worker to a client. First 23.13 and Sitting 3b, which proves the isolation and deploys with no stored key. Then 23.14 to 23.16 and Sitting 4.*

**In everyday life.** An office gives its owner a permanent key, which works until the lock is changed. A delivery driver gets no key at all. Each morning he shows his company badge at reception and gets a visitor pass that stops working at 6 p.m. If he loses the pass, it is useless by evening. If the owner loses the key, someone must notice and change the lock. In this concept, the permanent key is a stored API key, and the visitor pass is a short-lived token from workload identity.

**What you will learn.** The three ways a program can prove who it is to the platform, why a key that never ends is a risk, and how a program can avoid storing a key at all.

**Why it matters.** A stored key that leaks keeps working for whoever holds it. Each key you give an end date, or remove altogether, is one less secret to lose.

**One request, start to finish.** Two programs need to talk to the hosted platform. The deploy workflow in CI applies the agent files on every merge (23.4). The portal's server starts sessions all day. The builder works out how each should prove who it is.

1. **CI already has an identity.** Each run of a CI job can ask its own CI system for a short-lived signed token that says "this is the `agents.yml` workflow, in this repository, on the main branch".
2. **CI sends that token to the platform** and gets back a platform token that lasts one hour at most by default, and often only minutes, because it cannot outlast the CI system's own token by much. It applies the files, and the token expires.
3. **No key is stored in CI at all.**
4. **The portal's server has no such identity** on the host the lab uses for it. So it holds a stored key, kept as a secret on the server, limited to one workspace that has a monthly spending limit, and set to expire after 90 days.

Two programs, two answers, each the safest one available.

### How can a program prove who it is?

A program proves who it is with a static key or with workload identity. Either one can act for a service account:

- **A static key** is a long secret string, made once and stored by the program, like the API keys you made in Lab 21 (21.13). It works until someone deletes it, or until it expires. Because it lasts, it must be stored safely, changed on a schedule (key rotation), and given an end date where the platform allows one (key expiry). A leaked key without an end date works for the attacker until someone notices.
- **A service account** is not a way to prove anything. It is the identity a key or a token acts for: a program's identity, not a person's. Keys and tokens can belong to it, so they do not stop working when a person leaves, and it is added only to the workspaces it needs.
- Workload identity replaces the stored key altogether. It works in three steps, the same three as in the CI story above:
  1. The program asks the system it runs on, such as a CI system, for a short-lived signed token that names the program.
  2. It sends that token to the platform. The platform checks it against a rule set up in advance: "tokens for this repository's main branch may act as this service account".
  3. The platform returns its own short-lived token. The program uses it, and it expires.

  Nothing is stored. *For reference:* the system that issues the first token is an identity provider, the token is a JWT (Chapter 18), which follows OpenID Connect, and swapping it uses the JWT bearer grant of RFC 7523.

| | Static key | Workload identity |
| --- | --- | --- |
| What is stored | The key, until it is rotated or expires | Nothing. Tokens are issued on demand |
| How long a leaked credential works | Until it expires or is deleted | Until the short-lived token expires: from one minute to a day, one hour by default on the lab's platform, and never more than twice the life left on the CI token |
| What it needs | A safe place to store it | A system the program runs on that issues tokens, and a rule on the platform |
| Where the lab uses it | The portal's server, as a server secret, expiring in 90 days | CI, applying the agent files |

### Why do CI and the portal differ?

Workload identity needs an identity provider the platform trusts. CI has one. The portal's server, on the host the lab uses, has none that the platform's documents describe. So the portal uses the next safest thing: a key linked to a service account, that works only in one workspace with a monthly spending limit, expires on a date, and is rotated by a written step before it does. F6 has that step.

**At work.** In Lab 23, Task 13, Claude Code sets up workload identity for the CI workflow, with a rule that accepts only the main branch of this repository. It makes sure the repository's secrets hold no platform key, opens a pull request, and shows the builder its checks passing with no key and no platform token. After the merge, the merge job plans and applies, and the platform's record of the token exchange shows the rule that matched, whose target is the service account, not a person.

**The operating rule:** use workload identity wherever you can. Where a key remains, give it to a service account, one workspace with a spending cap, and an end date.
