# 22.5 Who decides whether a tool may run?

**In everyday life.** A company's expense rules work in layers. Some claims are allowed in advance, such as a taxi from the airport. Everything else goes to the finance team, which either decides on the spot or puts the claim in a tray for later. Either way, it applies the same rule. In this concept, the allowed list is the allow list, deciding on the spot is a permission callback, and the tray is an approval: the claim leaves the desk and comes back later.

**What you will learn.** How every tool call is checked in layers, and how one rule you write can decide a call at once, or later, after the run has stopped.

**Why it matters.** A tool that changes something must be decided by your rule, not by a setting an SDK picked for you.

**One request, start to finish.** Ana asks: "Flag every invoice for review." The model asks for `flag_invoice` with the invoice number `ALL`. One rule decides on both SDKs: `flag_invoice` may run only for one invoice, named as INV- and four digits, with a reason of at least ten characters. `ALL` fails.

1. **The first SDK asks at once.** It calls your function, a permission callback, which applies the rule and denies the call with a message. The run carries on at once.
2. **The second SDK hands it back.** The tool needs an approval, so the run pauses and returns the pending call to your code. Your code applies the same rule, rejects the call, and starts the run again from where it stopped. It could do that tomorrow.
3. On both, the model reads the message, and nothing is flagged. "Please flag INV-8316 for review" is allowed on both. A real model could instead flag the invoices one at a time, which the rule allows: a rule checks each call, not what the person meant.

### What decides whether a tool may run?

**Authorization** is deciding, by rules, whether a tool call may run. An approval is one way to do it later: the run pauses and hands the call back, and **resuming** starts it again from where it stopped. Either way the same rule decides.

### In what order is a tool call checked?

Every tool call is checked before it runs, in layers. Not every SDK has all five. The first SDK has all of them. The second SDK has no permission modes and no allow list: it has your tool list, approvals, and checks on each tool's input (code that checks a call's arguments before it runs).

| Layer | What it does | In this lab |
| --- | --- | --- |
| **Code around every call** | A **hook**: your code, run at a set moment, such as before every tool call. It may watch, change the input, or decide | One hook on the first SDK, which only logs |
| **Fixed rules** | Tools that are always denied, or always sent to your rule | None set |
| **A general setting** | The SDK's **permission mode**: its general answer for calls nothing else has decided | The lab names the mode `default`: it passes each undecided call on, so your rule gets the final say. One exception is below the table |
| **The allow list** | Tools that run without asking. This is a new list. Chapter 21's `allowOnly()` list, of every tool the worker was given, is now the tool list (22.4) | The connector's four read-only tools |
| **Your rule, for everything else** | A callback that answers at once, or an approval that hands the call back | Rule 1, `decideTool()` (in Python, `decide_tool()`), used by both SDKs |

**The exception in `default` mode.** On the first SDK, a few calls by built-in tools never ask anyone, such as a shell command that only reads, or reading a file in the working folder. They run without reaching your rule. The lab's worker cannot make such a call, because its built-in tools are off (22.4). Lab Task 5 turns them on for one run with a turn limit of 1, so whatever such a call reads never goes back to the model.

The layers decide in turn, and a deny ends it. An allow from a hook is not the last word: the call still meets the fixed rules, so a tool that is always denied stays denied. The read-only tools stop at the allow list, so your rule never sees them. Only the tool with an effect reaches your rule, which is what the lab wants. The allow list does not hide a tool. An agent SDK may offer the model every tool a connector lists, including one you never named, such as `next_invoice_page`, which Chapter 20 marked for its screen only, if your connector lists it. The lab's connector lists only its four read-only tools. On the first SDK, a call to a tool that is not on the allow list goes to your rule, apart from the exception above. So write the rule to say no to every tool it does not know, as rule 1 does. The second SDK has no allow list: every tool you give the agent runs when the model asks, unless you mark it as needing approval, and a connector's tools all count as given unless you filter them. In the lab, the connector's four tools run when asked, and only `flag_invoice` is marked.

### When should the run hand the call back?

A callback suits a decision your code can make at once. An approval suits a decision a person must make. The lab's second SDK also uses an approval for your rule, because an approval is the way that SDK decides a tool call (22.10). The run pauses and hands you the pending call, called an **interruption**, and its **run state**, a record of where it stopped. You can save the run state as text, so a manager can approve tomorrow, even after your program restarts. Resuming sends back approve or reject, and starts the run again from its saved state. Keep a saved run state as carefully as the conversation inside it (22.7). And load one only from storage you trust: on the second SDK, restoring a saved state does not check who saved it, or whether anyone changed it.

Write the rule once, as a plain function with tests, and call it from either shape.

### Which three defaults should you say out loud?

- **Name the setting yourself.** If you leave it out, some SDKs take it from the settings files on the computer, or use a mode where another model, not your rule, judges each call. Either way, your rule might not be the one deciding.
- **Never use a setting that skips every check,** such as the first SDK's mode `bypassPermissions`. The lab's `AGENTS.md`, the rules file your coding agents follow, forbids it.
- **A hook that fails does not block.** On the first SDK, a hook that throws an error counts as no decision by default. The call goes on to the other checks, and can still run. A hook that must block has to be set to block on failure.
