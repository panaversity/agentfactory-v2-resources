# 20.3 One turn: request, response and stop reason

**Where this fits.** This is step 3 of the loop, check. A response has come back. How does your program know whether the model is finished, or wants a tool?

**In everyday life.** A courier brings back your package with a slip stapled to it: "Delivered", "Recipient asked for a signature form", "Address incomplete", or "Refused". You do not open the box to find out what happened. You read the slip first, and it tells you what to do next. In this concept, the box is the response's content, and the slip is its **stop reason**.

**What you will learn.** What one round trip to the model carries each way, and how a single label on each reply tells your program what to do next.

**Why it matters.** Your program decides whether to go round again from that label alone. Read it wrong, and a loop stops too early or never stops.

**One request, start to finish.** The lab sends three questions to the first API. Here are the three responses, as neutral sketches. Each response is a list of **content blocks**, pieces of the answer, each with a type.

**Response 1.** "Which invoices are due this week?"

```text
content
  thinking     (the model's working notes. You need not read them, but they go back unchanged, 20.5)
  tool call    id A1   list_open_invoices   {"vendor_id": null, "due_on_or_before": "2027-04-04", "page_size": 10, "page": null}
stop reason    ?
```

*Predict:* why did it stop?

```text
stop reason    wants a tool        (the first API writes it as tool_use)
```

**Response 2.** "List every open invoice with its purchase order and its policy line", sent with a very small limit on output length.

```text
content
  text         "Here is every open invoice with its purchase order and policy line. INV-8301, Midwest
                Packaging Co., $4,825.00, matched to PO-7001 for $4,825.00, which"
stop reason    ?
```

*Predict:* the text stops mid-sentence. Why?

```text
stop reason    out of tokens       (max_tokens)
```

**Response 3.** A question the model will not answer.

```text
content        (usually little or none)
stop reason    refused             (refusal), with a short category and explanation
```

These responses follow the first API's documented shapes, with ids shortened to labels such as A1. They are illustrative, not from a live run, and your own run in Sitting 1 gives you real ones to compare.

### What does one turn carry?

Every call in the loop is one **turn**: one request, one response. A request carries three things: the **instructions** (what the worker is, set once and sent every time), the **conversation**, and the **tools**. A response carries the model's content and a **stop reason**, the reason the model stopped writing. One of those reasons needs a word you will use all chapter. A **token** is a small piece of text, often part of a word: "invoices" might be two tokens. You set a limit on how many tokens the model may write, and both APIs count and price everything in tokens (20.12). This is not the connector's sign-in token from Start here, which proves who is asking.

The loop's step 3 reads the stop reason and nothing else to decide what to do. Learn the first four rows. The other three are rare, and the loop handles them the same way, by ending:

| Stop reason (in plain words) | What it means | What your loop does |
| --- | --- | --- |
| Finished | The model gave its answer | End the loop. Show the answer |
| Wants a tool | The content holds one or more tool calls | Run them, return the results, call again (20.4) |
| Out of tokens | It hit the output limit you set, in tokens, mid-answer | End the loop and say the answer was cut short, or raise the limit and ask again |
| Refused | The model declined. This is a normal response, not an error | End the loop. Show the refusal. Never retry it as if it were a fault |
| Paused | Tools the provider runs on its own servers (such as a web search it runs for you) ran out of rounds, the number of times it may call them in one response | Only for tools the provider runs itself, which this chapter does not use |
| Hit a stop sequence | It wrote a string you asked it to stop at | This chapter sets none |
| Context window full | While writing, the model reached the most it can hold (its context window). A conversation already too long gets a 400 instead | End the loop. Chapter 27 covers long conversations |

The rule in the first API's own documentation is short: repeat while the stop reason is "wants a tool", and exit on any other. The lab's loop does exactly that (Task 3), so a stop reason it has never heard of still ends the loop safely.

### Declines, rejects or refuses: which is which?

Three words, three meanings. In this chapter, the model **declines** (its stop reason is "refused", a normal answer). The API **rejects** a request that is wrong, with an error such as a 400. And your code **refuses** a tool it should not run. Only the first is the model's choice.

### Is a refusal an error?

A refusal is not an error. The call succeeded. The response arrived with a normal status. Only its stop reason says the model declined. A loop that treats a refusal as a fault and retries will pay for the same refusal again and again.
