# 21.3 How does my code know why the model stopped?

**In everyday life.** A courier brings back your package with a slip stapled to it: "Delivered", "Recipient asked for a signature form", "Part delivered: the rest did not fit", or "Declined". You do not open the box to find out what happened. You read the slip first, and it tells you what to do next. In this concept, the box is the response's content, and the slip is its **stop reason**.

**What you will learn.** What one round trip to the model carries each way, and how a single label on each reply tells your program what to do next.

**Why it matters.** Your program decides whether to go round again from that label alone. Read it wrong, and a loop stops too early or never stops.

**Where this fits.** This is step 3 of the loop, check. A response has come back. How does your program know whether the model is finished, or wants a tool?

**One request, start to finish.** The lab sends three questions to the first API. Here are the three responses, as neutral sketches. Each response is a list of **content blocks**, pieces of the answer, each with a type.

**Response 1.** "Which invoices are due this week?"

**Response 2.** "List every open invoice with its purchase order and its policy line", sent with a very small limit on output length.

**Response 3.** A question the model will not answer.


These responses follow the first API's documented shapes, with ids shortened to labels such as A1. They are illustrative, not from a live run, and your own run in Sitting 1 gives you real ones to compare.

### What does one turn carry?

Every call in the loop is one **turn**: one request, one response. A request carries three things: the **instructions** (what the worker is, set once and sent every time), the **conversation**, and the **tools**. A response carries the model's content and a **stop reason**, the reason the model stopped writing. One of those reasons needs a word you will use all chapter. A **token** is a small piece of text, often part of a word: "invoices" might be two tokens. You set a limit on how many tokens the model may write, and both APIs count and price everything in tokens (21.12). This is not the connector's sign-in token from Start here, which proves who is asking.

The loop's step 3 reads the stop reason and nothing else to decide what to do. Learn the first four rows. The other three are rare, and the loop handles them the same way, by ending:

| Stop reason (in plain words, then the first API's word) | What it means | What your loop does |
| --- | --- | --- |
| Finished (`end_turn`) | The model gave its answer | End the loop. Show the answer |
| Wants a tool (`tool_use`) | The content holds one or more tool calls | Run them, return the results, call again (21.4) |
| Out of tokens (`max_tokens`) | It hit the output limit you set, in tokens, mid-answer | End the loop and say the answer was cut short, or raise the limit and ask again |
| Declined (`refusal`) | The model would not do what was asked. This is a normal response, not an error | End the loop and show what it said, or send the request to another model. Never retry it unchanged on the same model, as if it were a fault |
| Paused (`pause_turn`) | Some tools run on the provider's own servers, such as a web search it runs for you. They ran out of rounds, the most steps one response may take, so the response stopped part way. Sending it back lets them go on | End the loop. Only tools the provider runs itself pause, and this chapter uses none |
| Hit a stop sequence (`stop_sequence`) | It wrote a string you asked it to stop at | End the loop. This chapter sets none |
| Context window full (`model_context_window_exceeded`) | While writing, the model reached the most it can hold (its context window). A conversation already too long gets a 400 instead | End the loop. Chapter 26 covers long conversations |

The rule in the first API's own documentation is short: repeat while the stop reason is "wants a tool", and exit on any other. The lab's loop does exactly that (Task 3), so a stop reason it has never heard of still ends the loop safely.

### Declines, rejects or refuses: which is which?

Three words, three meanings. In this chapter, the model **declines** (its stop reason is "declined", a normal answer). The API **rejects** a request that is wrong, with an error such as a 400. And your code **refuses** a tool it should not run. Only the first is the model's choice. The API's own name for the declined stop reason is `refusal`: read it as "declined".

### Is "declined" an error?

No. The call succeeded, and the response arrived with a normal status. Only its stop reason says the model declined. A loop that retries it as a fault pays to be declined again.
