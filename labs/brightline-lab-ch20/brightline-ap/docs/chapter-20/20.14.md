# 20.14 How today's tools realize it

*Look things up here. You do not need to learn this section, only to know it is here.*

*Reference. Every fact here was read on its owner's own pages on November 5, 2026, unless it says otherwise. Facts marked **SDK types** were confirmed from the pinned SDK's own type definitions.*

**What you will learn.** How today's products carry the loop: the two main model APIs, and an open model on your own computer, with the facts that change how you write it.

**Why it matters.** Each product names the same steps its own way, and changes over time. This page is where you check the exact names before you build or run anything.

### Is there a standard for the loop's shapes?

No standard defines the loop's shapes. Both APIs, and the open-source servers that copy the second, carry the same loop in different JSON. The resemblance is not a shared standard. What is standard is around the loop: JSON Schema for tool inputs, server-sent events for streaming, OpenTelemetry for traces and MCP for the connector.

### Is every agent built this way?

Almost every agent in this book, and in the products you use, rests on one of these two APIs. It helps to see exactly how.

- **The two main APIs for talking to an LLM.** Anthropic's Claude Messages API and OpenAI's Responses API are the two main ways programs talk to large language models. Most other model vendors offer APIs compatible with one of them: the same request and response shapes, usually with only a different address and key. That is why this chapter's second-API loop can point at an open model with no code change (Task 12).
- **They are not agent-only APIs.** Most calls through them are not agents at all: chat, summaries, pulling data out of documents, sorting or translating text. Every call is the same thing: here is the input, write what comes next. Agents use a subset of features built for them: tool definitions, tool calls and tool results, stop reasons, and, on OpenAI's API, an optional stored conversation. Chapter 20 uses that subset.
- **Agent SDKs are a layer on top.** Claude's Agent SDK (Chapter 21) runs its loop on the Messages API. OpenAI's Agents SDK calls the Responses API by default, and can also use the older Chat Completions API. Both add the loop itself, retries, memory, handoffs between agents (one agent passing the work to another), guardrails (checks on what goes in and comes out) and tracing. Underneath, they do what this chapter does by hand: call, keep, check, run, return.
- **Where the line blurs.** Both APIs can now run some tools themselves, such as the provider's own web search or code execution, and the Messages API's MCP connector can call a connector for you. Then part of the loop runs on the provider's side, inside one API call (the "paused" stop reason in 20.3 comes from this). Hosted agent platforms (Chapter 22) go further and run the whole loop on the provider's side. The model calls are the same, but you no longer see them.
- **The point to keep.** Every agent is this loop around one of these two APIs. What differs is whose code runs the loop, and how much of it you can see.

### How does Anthropic's Claude Messages API realize it?

- **Versions and SDKs (20.13).** The API version `2026-10-21` is the newest, beside `2023-06-01` and `2023-01-01`, sent as the `anthropic-version` header by the SDK. The TypeScript SDK is `@anthropic-ai/sdk` 1.x (the lab pins 1.5.0, Node 20 or later), the first major on `2026-10-21`. The Python SDK is `anthropic` (the lab pins 2.5.0). The SDK sends the key as `Authorization: Bearer <key>` (SDK types and the lab's wire tests).
- **What `2026-10-21` removed (20.9).** A request with `temperature`, `top_p` or `top_k` is a 400, even at the default value. A `document` block in an assistant message is a 400.
- **Tools (20.2).** `name`, `description`, `input_schema` (JSON Schema), and optional `input_examples`, `strict` and `cache_control`. **Strict tool use** constrains the model's sampling to schema-valid inputs, generally available on every model. **Tool choice** is `auto` (the default with tools), `any`, `tool` or `none`. On Claude Opus 5.5, Sonnet 5.5, Fable 5.1 and Mythos 5.1, `any` and `tool` return a 400, and the documentation recommends `auto` with strict tool use.
- **The loop and stop reasons (20.1, 20.3).** Repeat while `stop_reason` is `tool_use`, exit on any other. Stop reasons: `end_turn`, `max_tokens`, `stop_sequence`, `tool_use`, `pause_turn` (a server-tool loop hit its limit, never for client tools), `refusal` (HTTP 200, with `stop_details`) and `model_context_window_exceeded` (the context window filled while the model was writing). `pause_turn` comes after a server-tool loop's limit, 10 rounds by default.
- **Tool calls and results (20.4).** A `tool_use` block has `id`, `name` and `input`. The answer is a `tool_result` block in the next user message, with `tool_use_id`, `content` and `is_error`. Results must come right after their calls, first in the content. Parallel calls get all their results together. `disable_parallel_tool_use` lives inside `tool_choice`.
- **State (20.5, 20.7).** Stateless: the full history on every request. Thinking blocks go back complete and unmodified, and the thinking setting cannot change inside a tool-use loop. The lab uses `thinking: {type: "adaptive"}`: the model decides when to think, and how much. A stateful option, **message threads**, is in beta (`message-threads-2026-08-12`): later turns send only new messages and the previous response's id, best effort (kept if possible, not guaranteed), expiring five minutes after the last request.
- **Streaming (20.11).** `message_start`, per block `content_block_start`, `content_block_delta` and `content_block_stop`, then `message_delta` and `message_stop`, with `ping` and `error`. Tool input arrives as `input_json_delta` with `partial_json`, joined and parsed at `content_block_stop`.
- **Errors and retries (20.9).** 400 `invalid_request_error`, 401 `authentication_error`, 402 `billing_error`, 403 `permission_error`, 404 `not_found_error`, 409 `conflict_error`, 413 `request_too_large`, 429 `rate_limit_error`, 500 `api_error`, 504 `timeout_error`, 529 `overloaded_error`. Every response has a `request-id` header. The SDKs retry connection errors, 408, 409, 429 and 500 and above twice by default, with exponential backoff, and time out after 10 minutes. Responses carry `_request_id`.
- **Caching (20.12).** `cache_control: {type: "ephemeral"}` on the request for automatic caching, or on up to four breakpoints. Five minutes by default, `ttl: "1h"` optional. Usage reports `cache_creation_input_tokens` and `cache_read_input_tokens` beside `input_tokens` and `output_tokens`.
- **The API can run the tools for you.** The MCP connector (beta, `mcp-client-2026-09-15`) lets the Messages API call a remote MCP server itself, returning `mcp_tool_use` and `mcp_tool_result` blocks, so your code never runs those tools. This chapter does not use it, because it moves step 4 of the loop out of your sight.
- **Other routes (20.13).** Claude models are also offered on Amazon Bedrock, Google Cloud (Claude Models on Google Cloud) and Microsoft Foundry, each with its own client setup, keys and regions.
- **Status and price.** Generally available, except the betas named. API usage at list price. New accounts get a small free credit to test the API, but there is no free plan.

### How does OpenAI's Responses API realize it?

- **SDKs (20.13).** `openai` for Node (the lab pins 7.51.0) needs Node 22 or later. The Python SDK is `openai` (the lab pins 3.46.0). The Responses API is the primary API, and Chat Completions is the previous standard, supported indefinitely. In Chat Completions, functions are not strict by default.
- **The older API.** You will still see `chat.completions` in older tutorials and Stack Overflow answers. It is the older API: OpenAI still supports it, but recommends Responses for all new projects. The ideas are the same. Only the JSON shape changed. The Assistants API, OpenAI's earlier API for assistants, was sunset (shut down) on August 26, 2026, and is no longer available.
- **Function tools (20.2).** `{type: "function", name, description, parameters, strict}`. Strict needs `additionalProperties: false` on every object and every property in `required`. In Responses, leaving `strict` out tries strict mode and falls back if the schema cannot be strict, so the lab sets `strict: true` explicitly. `tool_choice` is `auto`, `required`, a named function, `none` or `allowed_tools`. `parallel_tool_calls: false` means zero or one call.
- **Output items (20.6).** `function_call` items with `call_id`, `name` and `arguments`, a JSON string. `message` items. `reasoning` items, which must be passed back with the outputs of the calls they led to. Results go back as `{type: "function_call_output", call_id, output}`. The SDK has a helper, `toResponseInputItems()`, that turns output items into input items. The lab's loop does it by hand, in two lines, so you can see it.
- **The end of the loop (20.6).** No `function_call` items means the model is done. A response's `status` is `completed`, `failed`, `in_progress`, `cancelled`, `queued` or `incomplete` (SDK types), and an incomplete response has `incomplete_details.reason`, such as `max_output_tokens`.
- **State (20.7).** Responses are stored for 30 days by default. `store: false` turns that off. Stateless requests must keep every item in the output. Reasoning items carry `encrypted_content` by default in the current guides, and the lab also sets `include: ["reasoning.encrypted_content"]`, which is explicit and harmless. The stateful options are `previous_response_id`, which does not carry over the earlier `instructions` and bills all the input tokens of the chain of linked responses as input, and conversation objects, which are not subject to the 30-day limit. Organizations under zero data retention, an agreement under which OpenAI keeps no request content, get `store: false` automatically.
- **Retries (20.9).** Two retries with exponential backoff for connection errors, 408, 409, 429 and 500 and above, a 10-minute timeout, and `_request_id` from the `x-request-id` header.
- **Caching (20.12).** Usage reports `input_tokens_details.cached_tokens` and `cache_write_tokens` (SDK types), both counted inside `input_tokens`, as the lab assumes.
- **Status and price.** Generally available. API usage at list price, no free plan for API calls.

### How does an open model behind a local server realize it?

- **Ollama** offers `/v1/chat/completions` (tools, but no `tool_choice`) and `/v1/responses` with function calling, at `http://127.0.0.1:11434/v1/`. Only the stateless form of Responses is supported: no `previous_response_id` and no `conversation`, which fits this chapter exactly. Its documentation's examples use `qwen3` and `gpt-oss:20b`. The lab pins `qwen3:8b` until a live run shows which small model handles four tools best.
- **Alternatives.** vLLM offers Chat Completions and a Responses-compatible API with a tools example. llama.cpp's `llama-server` has chat completions and responses routes, with function calling documented on chat completions. LM Studio offers both on port 1234.
- **Security.** A local model server listens on your own computer. Keep it on `127.0.0.1`, never on every network address. Treat a downloaded model as untrusted code and data, from a source you chose.
- **Status and price.** Free to run, on your own hardware. You own the speed, the quality and the updates.

### Which differences change how you write the loop?

| | First API | Second API | Open model, local server |
| --- | --- | --- | --- |
| **Who keeps the conversation in this chapter** | You | You (`store: false`) | You (stateless only) |
| **How a call is matched to its result** | `tool_use.id` and `tool_use_id` | `call_id` on both | `call_id` on both |
| **How inputs arrive** | An object | A JSON string to parse | A JSON string, sometimes with wrong fields |
| **Failure in a result** | `is_error: true` | Text only (the lab writes `ERROR:`) | Text only |
| **What strict means by default** | Off unless you set it (strict is opt-in on each tool). The lab sets it explicitly | Tried unless set (the lab sets it) | Depends on the server and model |
| **How the loop knows it is done** | `stop_reason` is not `tool_use` | No `function_call` items, status `completed` | The same as the second API, but a reply cut short still says `completed` |
| **The model's reasoning** | Thinking blocks with a signature | Encrypted reasoning items | Varies by model |
| **Tested for this chapter** (a wire test captures exactly what the SDK sends) | Recorded and wire tests only, not yet live | Recorded and wire tests only, not yet live | Not yet |

### What is the loop's invariant?

The model only asks. Your code decides whether to run each tool, owns the whole conversation, and decides when the loop stops.
