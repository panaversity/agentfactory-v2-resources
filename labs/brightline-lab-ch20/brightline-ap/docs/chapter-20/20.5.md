# 20.5 The conversation is an array you own

**Where this fits.** This is step 2, keep. The model remembers nothing from one call to the next, so your program keeps the whole conversation and sends all of it every time. (The advisor from Start here forgets each note as soon as she answers it, so you slide the whole pile back under the door each time.)

**In everyday life.** A family doctor's practice brings in a fill-in doctor for one day. The fill-in doctor has never met the patient and will never see the file again after today. Everything the fill-in doctor needs is in the folder the clinic hands over: every note, every test, in order. If the clinic tears out a page, the fill-in doctor does not know it is missing, but the treatment may be wrong. In this concept, the fill-in doctor is the model, and the folder is the conversation array.

**What you will learn.** Why the model remembers nothing between calls, so your program keeps every message and sends all of them each time, unchanged.

**Why it matters.** Owning the whole history means you can print, test and replay exactly what the model saw. Editing it breaks the next call.

### What does a stateless API mean for the conversation?

The first API is **stateless**: it keeps nothing between calls. Each request must carry the whole history, and the model reads only what that request holds. So the conversation lives in your program, as a **conversation array**, a list of entries in order. Each entry has a role (the person, or the model) and content. The loop adds two entries on each turn that uses a tool: the model's content, then your results. On the last turn it adds only one, the model's answer. Your tool results go in an entry with the person's role, `user`, because the first API has no role of its own for tool results.

Three rules follow:

- **Everything the model produced goes back unchanged.** That includes text, tool calls and **thinking blocks**: the model's reasoning before it answers, which the first API returns as content blocks with a signature, a sealed code that proves the block was not changed. With tool use, the thinking that came with a tool call must be sent back, complete and unmodified, with that call. Rebuild the entry or edit a block, and the next request is rejected: a signature that was cut short or changed always gets a 400 error. Drop every thinking block and nothing fails, but the model loses its earlier reasoning.
- **Keep the same thinking setting for the whole loop.** The thinking setting says whether thinking is on, and how much the model may think. The documentation says it cannot change in the middle of a tool-use loop.
- **You may add, but do not rewrite the past.** You can add a new question at the end. Changing what the model said earlier makes the history untrue, and some of it, like thinking, the API checks.

### Why is a stateless API good news?

A stateless API means the whole conversation is in your hands, on your computer, in a variable you can print. You can log it, test it, replay it and see exactly what the model saw. Your tests in this lab do just that: they replay recorded responses and check, entry by entry, what the loop sent. Nothing is hidden on a server. 20.7 shows what changes when it is.

### What does sending the whole history cost?

Sending the whole history every time means every turn pays again for everything before it, in tokens and in time. A loop of six turns sends the instructions and tools six times. 20.12 shows how caching makes the repeated part cheap.
